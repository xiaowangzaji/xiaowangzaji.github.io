一、数据库基本概念

1.1 什么是数据库（DB）

数据库（Database, DB） 是长期存储在计算机内、有组织的、可共享的大量数据的集合。其特点：

  • 持久化存储：数据不因程序运行结束而消失
  • 有组织：数据按一定的数据模型组织、描述和存储
  • 可共享：数据可以被多个用户、多个应用共享使用
  • 冗余度小：数据独立性高，减少重复存储
  • 易扩展：可随需求灵活扩充

1.2 数据库管理系统（DBMS）

数据库管理系统（DBMS） 是位于用户与操作系统之间的一层数据管理软件，负责数据库的建立、使用和维护。

常见 DBMS：

DBMS类型特点
MySQL关系型开源、轻量、社区活跃
PostgreSQL关系型功能强大、支持复杂查询、JSON
Oracle关系型企业级、功能最全、收费
SQL Server关系型微软生态、Windows 友好
Redis键值型内存存储、极低延迟
MongoDB文档型灵活 Schema、BSON 格式
Elasticsearch搜索型全文检索、日志分析

1.3 数据模型

数据模型 是对现实世界数据特征的抽象，包含三个要素：

  1. 数据结构：描述数据的类型、内容、性质及数据间的联系
  2. 数据操作：增删改查等操作
  3. 数据约束：完整性规则集合

常见数据模型：

  • 层次模型：树形结构，节点间一对多关系（早期 IBM IMS）
  • 网状模型：图结构，节点间多对多关系
  • 关系模型：二维表结构，目前最主流
  • 面向对象模型：对象 + 类 + 继承
  • 文档模型：JSON/BSON 文档，如 MongoDB
  • 图模型：节点 + 边，如 Neo4j

1.4 数据库系统架构（三级模式结构）

外模式（用户视图）→ 模式（逻辑结构）→ 内模式（物理存储）
  • 外模式（子模式）：用户可见的局部逻辑结构
  • 模式（逻辑模式）：全体数据的全局逻辑结构
  • 内模式（存储模式）：数据的物理存储结构和存取方法

两级映像保证数据独立性：

  • 外模式/模式映像：保证逻辑数据独立性
  • 模式/内模式映像：保证物理数据独立性

二、关系型数据库核心概念

2.1 基本概念

术语说明对应关系模型概念
表（Table）二维表格结构关系（Relation）
行（Row）表中的一条记录元组（Tuple）
列（Column）表中的一个字段属性（Attribute）
主键（Primary Key）唯一标识一行的列候选键之一
外键（Foreign Key）引用其他表主键的列参照完整性约束

2.2 完整性约束

  • 实体完整性：主键不能为空且必须唯一
  • 参照完整性：外键值要么为 NULL，要么必须引用存在的主键值
  • 用户自定义完整性：业务规则约束（如年龄 > 0）

2.3 范式理论

范式（Normal Form） 是关系数据库设计的规范化标准，目的是消除数据冗余和操作异常。

第一范式（1NF）

要求：每个属性都不可再分，即表中每列都是原子值。

-- ❌ 违反 1NF：phone 列包含多个值
CREATE TABLE user (id INT, name VARCHAR(50), phone VARCHAR(100));
-- 数据示例: (1, '张三', '1380000,1390000')

-- ✅ 符合 1NF：拆分为多行
CREATE TABLE user_phone (user_id INT, phone VARCHAR(20));

第二范式（2NF）

要求：满足 1NF，且所有非主属性完全依赖于主键（消除部分依赖）。

主要针对复合主键的情况。如果主键只有一个字段，天然满足 2NF。

-- ❌ 违反 2NF：(order_id, product_id) 为复合主键
-- 但 product_name 只依赖于 product_id（部分依赖）
CREATE TABLE order_detail (
    order_id INT,
    product_id INT,
    product_name VARCHAR(100), -- 部分依赖 product_id
    quantity INT,
    PRIMARY KEY (order_id, product_id)
);

-- ✅ 符合 2NF：拆分
CREATE TABLE product (product_id INT PRIMARY KEY, product_name VARCHAR(100));
CREATE TABLE order_detail (order_id INT, product_id INT, quantity INT, PRIMARY KEY (order_id, product_id));

第三范式（3NF）

要求：满足 2NF，且所有非主属性不传递依赖于主键（消除传递依赖）。

-- ❌ 违反 3NF：dept_name 传递依赖于 emp_id
-- emp_id → dept_id → dept_name
CREATE TABLE employee (
    emp_id INT PRIMARY KEY,
    emp_name VARCHAR(50),
    dept_id INT,
    dept_name VARCHAR(100),  -- 传递依赖
    dept_location VARCHAR(100)  -- 传递依赖
);

-- ✅ 符合 3NF：拆分
CREATE TABLE department (dept_id INT PRIMARY KEY, dept_name VARCHAR(100), dept_location VARCHAR(100));
CREATE TABLE employee (emp_id INT PRIMARY KEY, emp_name VARCHAR(50), dept_id INT, FOREIGN KEY (dept_id) REFERENCES department(dept_id));

BCNF（巴斯-科德范式）

要求：满足 1NF，且每一个决定因素都包含候选键（比 3NF 更严格）。

3NF 允许主属性对候选键的传递依赖，BCNF 不允许。

关系 R(U, F)，若 X→Y 且 Y⊄X，则 X 必包含候选键。

范式总结：

1NF ⊃ 2NF ⊃ 3NF ⊃ BCNF

实际开发中，通常满足 3NF 即可，过度规范化可能导致 JOIN 过多、查询性能下降，此时可适当反范式化（空间换时间）。

三、SQL 核心语法

3.1 DDL（数据定义语言）

-- 创建数据库
CREATE DATABASE mydb CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

-- 删除数据库
DROP DATABASE IF EXISTS mydb;

-- 创建表
CREATE TABLE users (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    username VARCHAR(50) NOT NULL UNIQUE,
    email VARCHAR(100) NOT NULL,
    password_hash CHAR(64) NOT NULL,
    status TINYINT DEFAULT 1 COMMENT '0=禁用 1=正常',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_email (email),
    INDEX idx_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 修改表结构
ALTER TABLE users ADD COLUMN phone VARCHAR(20) AFTER email;
ALTER TABLE users DROP COLUMN phone;
ALTER TABLE users MODIFY COLUMN username VARCHAR(100) NOT NULL;
ALTER TABLE users CHANGE COLUMN email user_email VARCHAR(100) NOT NULL;

-- 创建索引
CREATE INDEX idx_username ON users(username);

-- 删除表
DROP TABLE IF EXISTS users;
TRUNCATE TABLE users;  -- 清空表数据但保留结构

3.2 DML（数据操作语言）

-- 插入数据
INSERT INTO users (username, email, password_hash) VALUES
    ('zhangsan', 'zhangsan@example.com', 'hash1'),
    ('lisi', 'lisi@example.com', 'hash2');

-- 更新数据
UPDATE users SET status = 0 WHERE id = 1;

-- 删除数据
DELETE FROM users WHERE id = 1;

3.3 DQL（数据查询语言）—— 重点

-- 基本查询
SELECT id, username, email FROM users WHERE status = 1;

-- 排序
SELECT * FROM users ORDER BY created_at DESC, username ASC;

-- 分组聚合
SELECT status, COUNT(*) AS cnt, MAX(created_at) AS latest
FROM users
GROUP BY status
HAVING cnt > 10;

-- 分页
SELECT * FROM users ORDER BY id LIMIT 20 OFFSET 40;  -- 第3页，每页20条
SELECT * FROM users ORDER BY id LIMIT 40, 20;         -- 等价写法

-- 多表 JOIN
SELECT u.username, o.order_no, o.amount
FROM users u
INNER JOIN orders o ON u.id = o.user_id
WHERE o.amount > 100
ORDER BY o.created_at DESC;

-- 子查询
SELECT * FROM users WHERE id IN (SELECT user_id FROM orders WHERE amount > 1000);

-- EXISTS 子查询（通常比 IN 更高效）
SELECT * FROM users u WHERE EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.id AND o.amount > 1000
);

-- UNION（去重合并）
SELECT username FROM users WHERE status = 1
UNION
SELECT username FROM users_archive WHERE status = 1;

-- CASE WHEN
SELECT
    username,
    CASE status
        WHEN 0 THEN '禁用'
        WHEN 1 THEN '正常'
        ELSE '未知'
    END AS status_text
FROM users;

3.4 DCL（数据控制语言）

-- 创建用户
CREATE USER 'app_user'@'%' IDENTIFIED BY 'StrongP@ss123';

-- 授予权限
GRANT SELECT, INSERT, UPDATE ON mydb.* TO 'app_user'@'%';
GRANT ALL PRIVILEGES ON mydb.* TO 'admin_user'@'localhost' WITH GRANT OPTION;

-- 撤销权限
REVOKE DELETE ON mydb.* FROM 'app_user'@'%';

-- 查看权限
SHOW GRANTS FOR 'app_user'@'%';

-- 刷新权限
FLUSH PRIVILEGES;

四、索引原理

4.1 B+ 树索引

MySQL InnoDB 默认使用 B+ 树 作为索引结构：

        [根节点]
       /    |    \
  [内部节点] [内部节点] [内部节点]
   /  \      /  \      /   \
[叶子节点][叶子节点][叶子节点][叶子节点]← 双向链表连接

B+ 树特点：

  • 非叶子节点只存储键值，不存储数据，单节点可容纳更多键，树更矮胖
  • 所有数据都存储在叶子节点
  • 叶子节点之间用双向链表连接，范围查询高效
  • 查询稳定：任何查询都要从根到叶子，O(log n)

与 B 树对比：

特性B 树B+ 树
数据存储所有节点都存仅叶子节点存
范围查询需要中序遍历叶子链表直接扫
树高相对较高更矮胖
查询稳定性不同深度不同都是 O(log n)

一般 3 层 B+ 树可存储约 2000 万行数据（每页 16KB，每行 1KB 估算）。

4.2 聚簇索引 vs 非聚簇索引

特性聚簇索引（Clustered Index）非聚簇索引（Secondary Index）
数据存储叶子节点存完整行数据叶子节点存主键值
数量每表只有一个（通常是主键）可以有多个
查询过程直接拿到数据需要回表查聚簇索引
InnoDB主键 = 聚簇索引其他索引 = 二级索引

回表查询：二级索引查到的主键值，再去聚簇索引中查完整数据。

4.3 覆盖索引

覆盖索引：查询的列全部包含在索引中，无需回表。

-- 假设 (username, email) 有联合索引
SELECT username, email FROM users WHERE username = 'zhangsan';  -- ✅ 覆盖索引
SELECT username, email, phone FROM users WHERE username = 'zhangsan';  -- ❌ 需回表

判断方式：EXPLAIN 的 Extra 列显示 Using index。

4.4 联合索引与最左前缀原则

CREATE INDEX idx_name_email ON users(username, email, status);

最左前缀原则：联合索引按最左侧开始匹配。

查询条件是否使用索引说明
WHERE username = ?✅匹配最左列
WHERE username = ? AND email = ?✅从左到右连续匹配
WHERE username = ? AND status = ?✅ 部分username 用索引，status 跳过
WHERE email = ?❌跳过了最左列
WHERE username LIKE 'zhang%'✅前缀匹配
WHERE username LIKE '%san'❌左模糊，全表扫描

4.5 索引失效场景

  1. 函数/表达式操作：WHERE YEAR(created_at) = 2024 ❌
  2. 隐式类型转换：字符串字段不用引号 WHERE phone = 1380000 ❌
  3. OR 条件：一个条件有索引，另一个没有 → 全表扫描
  4. NOT/!=/<>：通常不走索引
  5. 左模糊 LIKE：LIKE '%abc' ❌
  6. 数据量太小：优化器判断全表扫描更快

五、事务与 ACID 特性

5.1 事务（Transaction）

事务是一组要么全部执行成功、要么全部失败的数据库操作。

-- 开启事务
START TRANSACTION;

-- 一系列操作
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

-- 提交或回滚
COMMIT;  -- 或 ROLLBACK;

5.2 ACID 特性

特性含义实现机制
A 原子性事务要么全部完成，要么全部不完成undo log（回滚日志）
C 一致性事务前后数据保持一致性状态由应用层 + 其他三个特性共同保证
I 隔离性并发事务互不干扰锁 + MVCC
D 持久性事务提交后数据永久保存redo log（重做日志）

redo log vs undo log：

日志作用层级
redo log记录"做了什么"，用于崩溃恢复，保证持久性InnoDB 引擎层
undo log记录"修改前的值"，用于回滚和 MVCC，保证原子性InnoDB 引擎层
binlog记录所有修改操作，用于主从复制和 PITRMySQL Server 层

六、隔离级别与并发问题

6.1 并发问题

问题描述举例
脏读（Dirty Read）读到其他事务未提交的数据A 更新但未提交，B 读到了这个值
不可重复读（Non-repeatable Read）同一事务内两次读到不同值（数据被修改）A 第一次读 x=1，B 修改并提交，A 第二次读 x=2
幻读（Phantom Read）同一事务内两次查询结果行数不同（数据被插入/删除）A 查到 5 行，B 插入一行并提交，A 再查有 6 行

6.2 四种隔离级别

隔离级别脏读不可重复读幻读
读未提交（Read Uncommitted）⚠️ 可能⚠️ 可能⚠️ 可能
读已提交（Read Committed, RC）✅ 解决⚠️ 可能⚠️ 可能
可重复读（Repeatable Read, RR）✅ 解决✅ 解决✅ 解决（InnoDB 通过 MVCC + 间隙锁）
串行化（Serializable）✅ 解决✅ 解决✅ 解决
-- 查看/设置隔离级别
SELECT @@transaction_isolation;
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;

MySQL InnoDB 默认隔离级别为 RR（可重复读），Oracle 默认是 RC（读已提交）。

七、MVCC（多版本并发控制）

7.1 MVCC 原理

MVCC 通过保存数据的历史版本，实现读写不阻塞，提高并发性能。

核心机制：

  1. 隐藏列：每行数据有隐藏列

    • DB_TRX_ID：最近修改的事务 ID
    • DB_ROLL_PTR：回滚指针，指向 undo log 中的历史版本
    • DB_ROW_ID：隐藏主键（无主键时自动生成）

  2. undo log 版本链：每次修改生成新版本，通过回滚指针串联

  3. Read View（读视图）：事务开启时生成的快照，包含：

    • trx_ids：活跃事务 ID 列表
    • low_limit_id：最大事务 ID + 1（大于此值的数据对当前事务不可见）
    • high_limit_id：最小活跃事务 ID（小于此值的数据可见）
    • creator_trx_id：当前事务 ID

7.2 可见性判断规则

对于某行数据的 DB_TRX_ID：
1. 如果 DB_TRX_ID < high_limit_id → 数据已提交，可见 ✅
2. 如果 DB_TRX_ID >= low_limit_id → 数据未提交或后生成，不可见 ❌
3. 如果 high_limit_id <= DB_TRX_ID < low_limit_id：
   a. DB_TRX_ID 在 trx_ids 中 → 活跃事务生成，不可见 ❌
   b. DB_TRX_ID 不在 trx_ids 中 → 已提交，可见 ✅

7.3 RC 与 RR 的 MVCC 区别

隔离级别Read View 生成时机效果
RC（读已提交）每次 SELECT 都生成每次读到最新已提交的数据
RR（可重复读）第一次 SELECT 时生成，后续复用整个事务看到同一份快照

八、锁机制

8.1 锁的分类

按粒度：表级锁 → 页级锁 → 行级锁
按性质：共享锁（S 锁/读锁）、排他锁（X 锁/写锁）
按算法：意向锁、记录锁、间隙锁、临键锁

8.2 InnoDB 行级锁

锁类型说明场景
记录锁（Record Lock）锁定索引记录SELECT ... FOR UPDATE
间隙锁（Gap Lock）锁定索引记录之间的间隙，防止插入RR 级别下的范围查询
临键锁（Next-Key Lock）记录锁 + 间隙锁RR 级别下的范围查询，解决幻读
意向锁（Intention Lock）表级锁，表示事务打算在行上加什么锁自动添加，用于快速判断表锁兼容性

意向锁兼容性：

ISIX
IS✅✅
IX✅✅
表级 S 锁✅❌
表级 X 锁❌❌

8.3 死锁（Deadlock）

死锁条件（四个必要条件同时满足）：

  1. 互斥：资源一次只能被一个事务占用
  2. 占有并等待：事务已占有资源，还在等待其他资源
  3. 不可抢占：资源不能被强制剥夺
  4. 循环等待：形成环路等待链

死锁处理：

-- 查看死锁
SHOW ENGINE INNODB STATUS;

-- 死锁检测（InnoDB 默认开启）
SHOW VARIABLES LIKE 'innodb_deadlock_detect';

-- 死锁超时时间
SET innodb_lock_wait_timeout = 50;  -- 默认 50 秒

预防死锁策略：

  • 固定顺序访问表和行
  • 大事务拆小事务
  • 降低隔离级别（RC 级别无间隙锁，减少死锁概率）
  • 使用 ORDER BY 确保加锁顺序一致

九、数据库设计三范式

同第二节范式理论，总结为：

  1. 1NF：列不可再分（原子性）
  2. 2NF：消除部分依赖（每列完全依赖主键）
  3. 3NF：消除传递依赖（非主列不间接依赖主键）

反范式化场景：

  • 读多写少的高并发场景（如商品详情冗余库存）
  • 数据仓库 OLAP 场景（星型模型、雪花模型）
  • 日志/流水表（按时间分区，不做严格范式）

十、性能优化

10.1 慢查询分析

-- 开启慢查询日志
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL slow_query_log_file = '/var/log/mysql/slow.log';
SET GLOBAL long_query_time = 2;  -- 超过 2 秒的记录

-- 使用 EXPLAIN 分析 SQL
EXPLAIN SELECT * FROM users WHERE username = 'zhangsan';

10.2 EXPLAIN 关键字段

字段说明
type访问类型：ALL < index < range < ref < eq_ref < const < system
possible_keys可能使用的索引
key实际使用的索引
key_len使用的索引长度（越长越精确）
rows预估扫描行数
ExtraUsing index=覆盖索引，Using filesort=需要排序，Using temporary=临时表

type 从最差到最优：

ALL（全表扫描）→ index（全索引扫描）→ range（范围扫描）→
ref（非唯一索引查找）→ eq_ref（唯一索引查找）→
const/const（主键或唯一索引等值）→ system（系统表）

10.3 分库分表

垂直拆分：按业务模块拆分数据库，按字段冷热拆分表。

水平拆分：

  • 分表策略：Range（按范围）、Hash（取模）、一致性 Hash
  • 分库策略：同分表，但需考虑跨库 JOIN 和分布式事务
  • 中间件：ShardingSphere、MyCat、Vitess

分库分表带来的问题：

  1. 分布式事务：2PC、TCC、Saga、本地消息表
  2. 跨库 JOIN：应用层组装、冗余字段、全局表
  3. 排序分页：各分片排序后合并
  4. 全局唯一 ID：雪花算法（Snowflake）、UUID、号段模式
  5. 数据迁移：双写迁移、增量同步

十一、NoSQL 概述

11.1 Redis（键值存储）

  • 数据结构：String、List、Set、Sorted Set、Hash
  • 特点：内存存储、单线程模型、支持持久化（RDB/AOF）
  • 应用场景：缓存、会话存储、排行榜、分布式锁、计数器
  • 持久化：
    • RDB：快照，恢复快但可能丢数据
    • AOF：追加日志，数据完整但文件大
    • 混合持久化：RDB + AOF（推荐）

11.2 MongoDB（文档数据库）

  • 数据格式：BSON（Binary JSON）
  • 特点：Schema-free、支持索引、聚合管道
  • 应用场景：内容管理、日志存储、实时分析

11.3 Elasticsearch（搜索/分析引擎）

  • 核心概念：Index（索引）、Document（文档）、Type（类型，7.x 已废弃）
  • 底层：基于 Lucene 倒排索引
  • 特点：全文检索、近实时、分布式
  • 应用场景：日志分析（ELK）、商品搜索、全文检索

十二、常见面试要点速记

1. 一条 SQL 查询的执行过程：
   连接器 → 查询缓存（8.0 已移除）→ 解析器 → 优化器 → 执行器 → 存储引擎

2. 一条 SQL 更新的执行过程：
   执行器 → 存储引擎 → 记录 redo log（prepare）→ 记录 binlog → 提交事务（commit redo log）
   （两阶段提交保证 redo log 和 binlog 一致性）

3. 为什么用 B+ 树而不用 Hash/二叉树/B 树？
   - Hash：等值查询快，范围查询不行
   - 二叉树：可能退化成链表，树太高
   - B 树：非叶子节点也存数据，单节点容量小，范围查询弱

4. COUNT(*) vs COUNT(1) vs COUNT(字段)：
   - COUNT(*) 和 COUNT(1) 在 InnoDB 中无区别
   - COUNT(字段) 不统计 NULL 值
   - COUNT(*) MySQL 8.0 有专门优化

5. 为什么 InnoDB 用自增主键最好？
   - 数据按主键顺序插入，页分裂少
   - B+ 树叶子节点有序且连续
   - 非自增主键导致频繁页分裂和页合并
