一、网络体系结构

1.1 OSI 七层参考模型

┌──────────────────────────────────────────┐
│  第7层  应用层（Application）    HTTP/FTP/DNS/SMTP │
├──────────────────────────────────────────┤
│  第6层  表示层（Presentation）  加密/压缩/格式转换  │
├──────────────────────────────────────────┤
│  第5层  会话层（Session）       建立/管理/终止会话  │
├──────────────────────────────────────────┤
│  第4层  传输层（Transport）     TCP/UDP/端口号      │
├──────────────────────────────────────────┤
│  第3层  网络层（Network）       IP/路由/ICMP        │
├──────────────────────────────────────────┤
│  第2层  数据链路层（Data Link）  MAC/以太网/帧       │
├──────────────────────────────────────────┤
│  第1层  物理层（Physical）      比特流/电缆/光纤     │
└──────────────────────────────────────────┘

1.2 TCP/IP 四层模型

┌──────────────────────────────────────────┐
│  应用层        HTTP/HTTPS/DNS/FTP/SMTP    │ ← OSI 5~7层合并
├──────────────────────────────────────────┤
│  传输层        TCP/UDP                    │ ← 对应 OSI 第4层
├──────────────────────────────────────────┤
│  网络层（网际层）IP/ICMP/ARP              │ ← 对应 OSI 第3层
├──────────────────────────────────────────┤
│  网络接口层     以太网/WiFi/PPP            │ ← OSI 1~2层合并
└──────────────────────────────────────────┘

1.3 数据封装与解封装

发送端：数据 → 段（TCP/UDP）→ 包（IP）→ 帧（MAC）→ 比特流（物理信号）
接收端：比特流 → 帧 → 包 → 段 → 数据

每层添加自己的头部（Header），到达对等层后剥去头部，交给上层。

二、物理层与数据链路层

2.1 物理层概述

  • 功能：在物理介质上传输原始比特流
  • 传输介质：双绞线、同轴电缆、光纤、无线电波
  • 编码方式：曼彻斯特编码、差分曼彻斯特编码

2.2 数据链路层

  • 功能：将比特流组装为帧（Frame），提供差错检测和流量控制
  • MAC 地址：48 位硬件地址，全球唯一（前 24 位厂商编号 + 后 24 位序列号）
  • 以太网帧格式：目的 MAC（6）+ 源 MAC（6）+ 类型（2）+ 数据（46~1500）+ FCS（4）
  • MTU：最大传输单元，以太网默认 1500 字节
  • CSMA/CD：载波监听多点接入/碰撞检测（半双工以太网）

三、网络层

3.1 IP 协议

  • 功能：提供无连接、不可靠的数据报传输服务
  • IP 地址：唯一标识网络中的主机
  • TTL（Time To Live）：每经过一个路由器减 1，为 0 时丢弃，防止环路

3.2 IPv4 vs IPv6

特性IPv4IPv6
地址长度32 位（约 43 亿）128 位
地址表示点分十进制：192.168.1.1冒号十六进制：2001:0db8::1
头部长度20 字节（可变）40 字节（固定）
配置方式手动或 DHCP自动配置（SLAAC）
安全性IPSec 可选IPSec 内置支持
分片路由器可分片仅源端可分片

3.3 IPv4 地址分类

特殊地址：

  • 127.0.0.1：回环地址（localhost）
  • 10.x.x.x、172.16.x.x~172.31.x.x、192.168.x.x：私有地址
  • 0.0.0.0：所有地址/默认路由

3.4 子网划分

子网掩码：用于区分网络号和主机号。

IP:       192.168.1.100   → 11000000.10101000.00000001.01100100
Mask:     255.255.255.0   → 11111111.11111111.11111111.00000000
Network:  192.168.1.0     → 11000000.10101000.00000001.00000000

CIDR（无类别域间路由）：用 /n 表示网络前缀长度。

  • 192.168.1.0/24：前 24 位为网络号，可用主机 254 台
  • 10.0.0.0/8：前 8 位为网络号，可用主机约 1677 万台

3.5 NAT（网络地址转换）

作用：将私有 IP 转换为公有 IP，解决 IPv4 地址不足。

类型说明
静态 NAT一对一固定映射
动态 NAT地址池动态分配
NAPT/PAT多对一，通过端口号区分（最常见）
内网主机 A(192.168.1.2:5000) → NAT 路由器(203.0.113.1:6000) → 公网服务器
内网主机 B(192.168.1.3:5000) → NAT 路由器(203.0.113.1:6001) → 公网服务器

3.6 路由协议

协议类型算法适用场景
RIPIGP（内部网关）距离向量（跳数）小型网络

四、ARP 协议

ARP（Address Resolution Protocol）：IP 地址 → MAC 地址的映射。

工作原理：

  1. 主机 A 查 ARP 缓存，有 B 的 MAC → 直接发送
  2. 无缓存 → A 发送 ARP 请求（广播）："谁有 IP 192.168.1.2？请告诉 MAC"
  3. B 收到请求 → 回复 ARP 响应（单播）："我有，MAC 是 AA:BB:CC:DD:EE:FF"
  4. A 缓存该映射

ARP 缓存：条目有 TTL，超时自动清除。

RARP（反向 ARP）：MAC → IP，现已基本被 DHCP 取代。

六、TCP 三次握手与四次挥手

6.1 三次握手（建立连接）

客户端 (CLOSED → SYN_SENT → ESTABLISHED)
    │
    │ SYN=1, seq=x
    │─────────────────────────────────►
    │                                 服务端 (LISTEN → SYN_RCVD → ESTABLISHED)
    │◄────────────────────────────────│
    │ SYN=1, ACK=1, seq=y, ack=x+1   │
    │                                 │
    │ ACK=1, seq=x+1, ack=y+1        │
    │─────────────────────────────────►
    │                                 │

详细步骤：

  1. 第一次握手：客户端发送 SYN=1，seq=x，进入 SYN_SENT 状态
  2. 第二次握手：服务端回复 SYN=1, ACK=1，seq=y, ack=x+1，进入 SYN_RCVD
  3. 第三次握手：客户端发送 ACK=1，seq=x+1, ack=y+1，双方进入 ESTABLISHED

为什么需要三次？

  • 防止已失效的连接请求（延迟报文）到达服务端，导致服务端误建立连接
  • 双方都需要确认对方的收发能力正常

TCP 状态转换：

CLOSED → [发送SYN] → SYN_SENT → [收到SYN+ACK] → ESTABLISHED
LISTEN → [收到SYN] → SYN_RCVD → [收到ACK] → ESTABLISHED

6.2 四次挥手（断开连接）

客户端 (ESTABLISHED → FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED)
    │
    │ FIN=1, seq=u
    │─────────────────────────────────►
    │                                 服务端 (ESTABLISHED → CLOSE_WAIT → LAST_ACK → CLOSED)
    │ ACK=1, seq=v, ack=u+1          │
    │◄────────────────────────────────│
    │                                 │ [服务端完成数据发送后]
    │ FIN=1, ACK=1, seq=w, ack=u+1  │
    │◄────────────────────────────────│
    │ ACK=1, seq=u+1, ack=w+1        │
    │─────────────────────────────────►
    │ [等待 2MSL]                     │
    ▼                                 ▼
 CLOSED                            CLOSED

详细步骤：

  1. 第一次：客户端发送 FIN=1, seq=u，进入 FIN_WAIT_1（不再发送数据）
  2. 第二次：服务端回复 ACK=1, ack=u+1，进入 CLOSE_WAIT，客户端进入 FIN_WAIT_2

    此时客户端→服务端方向关闭，但服务端仍可发送数据（半关闭状态）

  3. 第三次：服务端数据发送完毕，发送 FIN=1, ACK=1, seq=w, ack=u+1，进入 LAST_ACK
  4. 第四次：客户端回复 ACK=1, ack=w+1，进入 TIME_WAIT，服务端进入 CLOSED

TIME_WAIT 的作用：

  1. 确保最后一个 ACK 到达服务端：若丢失，服务端重传 FIN，客户端还在 TIME_WAIT 可重新回复
  2. 让旧连接的报文在网络中消散：等待 2MSL（约 4 分钟），避免旧报文干扰新连接

为什么客户端最后要等待 2MSL？

  • MSL（Maximum Segment Lifetime）：报文在网络中的最长生存时间
  • 2MSL = 发送 FIN + 收到 FIN 的重传超时，确保网络中不再有本连接的报文

大量 TIME_WAIT 的优化：

# Linux 内核参数优化
net.ipv4.tcp_tw_reuse = 1        # 允许 TIME_WAIT socket 重用（推荐）
net.ipv4.tcp_max_tw_buckets = 5000  # TIME_WAIT 最大数量

6.3 所有 TCP 状态汇总

状态说明
CLOSED初始状态
LISTEN服务端等待连接
SYN_SENT已发送 SYN，等待确认
SYN_RCVD已收到 SYN 并发送 SYN+ACK
ESTABLISHED连接已建立，数据传输中
FIN_WAIT_1已发送 FIN，等待 ACK
FIN_WAIT_2已收到 ACK，等待对方 FIN
TIME_WAIT已发送最后一个 ACK，等待 2MSL
CLOSE_WAIT已收到 FIN，等待应用层关闭
LAST_ACK已发送 FIN，等待 ACK
CLOSING双方同时发送 FIN 的特殊情况

七、TCP 可靠传输机制

7.1 序列号与确认应答

  • 序列号（seq）：TCP 按字节编号，保证有序性和去重
  • 确认号（ack）：期望收到的下一个字节序号，ack = 收到的 seq + 数据长度
  • 确认应答（ACK）：收到数据后回复确认，实现可靠传输

7.2 超时重传

发送方发送数据后启动重传定时器，若超时未收到 ACK 则重传。

  • RTO（Retransmission Timeout）：动态计算，基于 RTT（Round Trip Time）

7.3 滑动窗口

发送窗口 = [已发送未确认] + [可发送未发送] 接收窗口（rwnd） = 接收方剩余缓冲区大小

│ 已确认 │ 已发送未确认 │ 可发送 │ 不可发送 │
0       ↑             ↑      ↑         ↑
      ack          window_start    send_buffer_end

特点：

  • 发送方不必等 ACK 就可以连续发送（提高吞吐量）
  • 窗口大小由接收方通告（rwnd 字段）
  • 累积确认：ACK 号为 N 表示 N 之前所有字节都已收到

7.4 拥塞控制

拥塞控制 vs 流量控制：

  • 流量控制：端到端，防止发送方压垮接收方（滑动窗口）
  • 拥塞控制：全局性，防止过多数据压垮网络

四大算法：

算法窗口变化目的
慢启动（Slow Start）cwnd 每 RTT 翻倍（指数增长）快速探测可用带宽
拥塞避免（Congestion Avoidance）cwnd 每 RTT +1 MSS（线性增长）谨慎接近拥塞点
拥塞发生（Fast Retransmit）收到 3 个重复 ACK，立即重传不等待超时快速恢复
快速恢复（Fast Recovery）cwnd = ssthresh，线性增长避免慢启动的重新探测

拥塞窗口（cwnd）变化图：

cwnd
  │       /|       /|        /\
  │      / |      / |       /  \
  │     /  |     /  |      /    \______
  │    /   |    /   |     /             \
  │   /    |   /    |    /               \
  │  /     |  /     |   /                 \
  │ /      | /      |  /                   \
  │/_______|/_______|_/                     \______
  └────────────────────────────────────────────────→ 时间
     慢启动   拥塞避免   超时→慢启动     快重传→快恢复

阈值（ssthresh）：慢启动与拥塞避免的分界点。

  • 初始值通常较大
  • 拥塞时减半：ssthresh = cwnd / 2
  • 超时发生时：cwnd = 1，重新慢启动

八、HTTP 协议演变

8.1 版本演进

版本年份核心特点
HTTP/0.91991仅支持 GET，只能返回 HTML，无头部
HTTP/1.01996引入状态码、MIME、POST/HEAD，每次请求新建连接
HTTP/1.11997持久连接（Keep-Alive）、管道化、分块传输、虚拟主机、缓存控制
HTTP/22015二进制分帧、多路复用、头部压缩（HPACK）、服务端推送、流优先级
HTTP/32022基于 QUIC（UDP），解决 TCP 队头阻塞、0-RTT 建连

8.2 HTTP/1.1 核心特性

持久连接（Keep-Alive）：

  • 默认保持连接，多次请求复用同一 TCP 连接
  • 减少握手开销，提升性能

管道化（Pipelining）：

  • 客户端可以在同一连接上连续发送多个请求，不需等待响应
  • 但响应必须按请求顺序返回 → 队头阻塞问题

缓存机制：

Cache-Control: max-age=3600, no-cache, no-store, must-revalidate
ETag: "abc123"
If-None-Match: "abc123"
Last-Modified: Wed, 15 May 2026 10:00:00 GMT
If-Modified-Since: Wed, 15 May 2026 10:00:00 GMT

8.3 HTTP/2 核心特性

  • 二进制分帧层：将 HTTP 消息拆分为二进制帧
  • 多路复用：同一连接上并行多个请求响应流，互不阻塞
  • 头部压缩（HPACK）：维护静态/动态表，减少重复头部
  • 服务端推送：服务端主动推送资源（浏览器已逐渐禁用）
  • 流优先级：客户端指定资源加载优先级

8.4 HTTP/3（QUIC）

  • 基于 UDP，在应用层实现可靠传输
  • 彻底解决 TCP 队头阻塞
  • 0-RTT 建连（首次 1-RTT，后续 0-RTT）
  • 连接迁移（IP 变化无需重连，用 Connection ID 标识）

加密体系：

  1. 非对称加密（握手阶段）：RSA/ECC，用于协商对称密钥
    • 公钥加密，私钥解密
    • 解决密钥配送问题
  2. 对称加密（通信阶段）：AES/ChaCha20，用于实际数据传输
    • 加密解密用同一密钥
    • 效率高，适合大量数据
  3. 消息认证码（MAC）：HMAC，保证数据完整性

10.3 CA 证书

网站证书 → 中间 CA 证书 → 根 CA 证书（浏览器内置信任）

证书内容：域名、颁发者、有效期、公钥、签名算法。

十二、从输入 URL 到页面展示的完整过程

1. DNS 解析：域名 → IP 地址
2. TCP 连接：三次握手（HTTP/3 则是 QUIC 建连）
3. TLS 握手：HTTPS 协商加密（HTTP 无此步）
4. HTTP 请求：发送 GET/POST 请求
5. 服务端处理：路由、业务逻辑、查询数据库、生成响应
6. HTTP 响应：返回 HTML/JSON 等
7. 浏览器渲染：
   a. 解析 HTML → 构建 DOM 树
   b. 解析 CSS → 构建 CSSOM 树
   c. DOM + CSSOM → 渲染树（Render Tree）
   d. 布局（Layout/Reflow）：计算每个节点的位置和大小
   e. 绘制（Paint）：将渲染树绘制到屏幕上
8. 加载子资源：解析到 <img>、<script>、<link> 等标签，发起额外请求
9. JavaScript 执行：解析并执行脚本，可能修改 DOM（触发重排/重绘）

  • 基于 TCP，全双工通信
  • 一次握手，持久连接
  • 服务端可主动推送数据

十四、CDN（内容分发网络）

14.1 CDN 工作原理

用户请求 → DNS 解析（智能 DNS 返回最近 CDN 节点 IP）
         → CDN 边缘节点
         → 有缓存：直接返回
         → 无缓存：回源站拉取 → 缓存 → 返回用户

14.2 CDN 核心概念

概念说明
源站原始服务器
边缘节点（Edge）离用户最近的 CDN 服务器
回源CDN 节点向源站请求资源
缓存命中率命中缓存的比例，越高越好
预热提前将内容分发到 CDN 节点
刷新强制清除 CDN 缓存

14.3 CDN 的优势

  • 加速访问：就近获取内容，降低延迟
  • 减轻源站压力：大量请求被 CDN 缓存拦截
  • 高可用：源站故障时 CDN 仍可返回缓存内容
  • 安全防护：DDoS 防护、WAF

十五、常见面试要点速记

1. TCP 和 UDP 的区别：
   - TCP 面向连接、可靠、有序、流量/拥塞控制、字节流
   - UDP 无连接、不可靠、无序、无拥塞控制、数据报

2. 三次握手和四次挥手：
   - 握手三次：防止历史连接、确认双方收发能力
   - 挥手四次：TCP 全双工，每个方向单独关闭
   - TIME_WAIT：2MSL，确保最后一个 ACK 到达

3. HTTP 1.1 vs 2.0 vs 3.0：
   - 1.1: 文本协议、持久连接、队头阻塞
   - 2.0: 二进制分帧、多路复用、头部压缩
   - 3.0: 基于 QUIC/UDP，解决 TCP 队头阻塞

4. HTTPS 加密过程：
   - 非对称加密协商密钥 + 对称加密传输数据 + MAC 保证完整性
   - 证书链验证防止中间人攻击

5. DNS 解析过程：
   - 浏览器缓存 → OS 缓存 → 递归 DNS → 根 → TLD → 权威
